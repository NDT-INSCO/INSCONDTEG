# جامعة إنسكو الروبوتية للإنشاءات الصناعية «الروبوت الجامعي»

آخر تحديث: نوفمبر 2026.
هذا الملف يشرح ما أُضيف إلى المنصة تنفيذًا لطلب «روبوت جامعي يجمع علوم
الإنشاءات الصناعية ويغذيها لوكلاء المنصة». المرجع التنفيذي هو الكود نفسه:
`src/data/university*.ts` · `src/ai/universityContract.ts` · `src/ai/universityClient.ts` ·
`server/university/*` · `src/components/academy/InscoUniversity*.tsx`.

---

## 1. الخلاصة في أربعة أسطر

- أكاديمية إنسكو صارت تحوي قسمًا جديدًا سابعًا: **«الجامعة الروبوتية»** (`#university`).
- الجامعة = **12 تخصصًا** (علوم، هندسة، رياضيات، جبر، مواد ولحام، إنشاء، أكواد ومعايير،
  سلامة، NDT، برمجة، علاقات عامة، تسويق) — في كل تخصص **روبوتَي جمع** من الإنترنت
  و**خلية عصبية** واحدة.
- ثلاثة أجهزة مركزية: **العميد** (رئيس الجامعة الروبوتي — التوجيه والتوزيع)،
  **«المُنظِّم»** (روبوت التنظيم والهيكلة — الأرشفة العلمية بأكواد `INSCO-IND-…`)،
  و**«المعمل»** (وحدة تعليم وكلاء الذكاء الاصطناعي بالمنصة — يولّد «حزم تعليم وكلاء»).
- كل سجل علمي موثق برابط HTTPS لناشر أصلي؛ كل ما يُجمع حيًّا من الإنترنت يُوسم
  **«قيد المراجعة»** ولا يُعتمد بلا مختص. لا أرقام مكتوبة يدويًا في الواجهة — العدادات
  تُحسب من البيانات.

## 3. كيف يعمل (الخط التشغيلي)

```
١ · العميد يوجّه المهمة إلى الروبوت المختص داخل القسم
٢ · روبوت الجمع يتصفح الإنترنت الحي (Gemini + Google Search) ويصيغ سجلات ثنائية اللغة
٣ · «المُنظِّم» يفحص: استشهادات HTTPS، كشف التكرار، إسناد أكواد INSCO-IND-<القسم>-NNN
٤ · الخلية العصبية تذاكر: تطبيع المفاتيح ← دمج المكرر ← رفع الإصدار ← إرجاع «قيد المراجعة»
٥ · «المعمل» يبني «حزمة تعليم وكيل»: ديباجة نظام + خلاصة علمية + أسئلة مراقبة + حدود
    → تُراجع بشريًا ثم تُحقن في وكيل المنصة (المستشار · وكيل ChatGPT · مجتمع INSCO…)
```

### الوحدات المركزية

| الوحدة | المعرف | المهمة |
| --- | --- | --- |
| العميد — الرئيس الجامعي الروبوتي | `rector` | توازن التوزيع بين الجمع والمراجعة، وإعلان أولويات كل موسم علمي |
| «المُنظِّم» — روبوت التنظيم والهيكلة والأرشفة | `archivist` | كود ثابت لكل سجل، تصنيف بالقسم، فحص اكتمال واستشهادات، فهرسة قابلة للبحث |
| النواة المركزية | `nucleus` | ربط خلايا الأقسام: كشف العلاقات بين التخصصات ومنع ازدواجية المعرفة |
| «المعمل» — وحدة تعليم وكلاء الذكاء الاصطناعي | `lab` | تحويل المعرفة المعتمدة إلى حزم تعليم وكلاء جاهزة للمراجعة والحقن |

## 4. الصراحة قبل أي شيء (Honesty contract)

1. **ما جُمع حيًّا لا يُعتمد تلقائيًا.** كل سجل من الإنترنت يدخل الأرشيف
   `pending-review`، ويرفع رقم إصداره عند أي دمج — ولا يُعرض كمرجع معتمد بلا توقيع مختص.
2. **النسخة الثابتة (GitHub Pages) لا تتظاهر بتصفح.** بلا `GEMINI_API_KEY` على الخادم
   تستجيب البوابة من الأرشيف الموثق المبدئي مع شارة صريحة «أرشيف موثق (لا بوابة)».
3. **الخلية العصبية دالة حتمية** (`mergeKnowledgeRecords`): تطبيع ← دمج ← ترقية إصدار ←
   إعادة إلى قائمة المراجعة. تعمل بلا إنترنت، وتعمل داخل المتصفح عند الحاجة.
4. **«المعمل» يولّد مسودات**، لا شهادات ولا وعود اعتماد. الحزم تُنسخ/تُنزَّل كملف
   Markdown لمراجعتها ثم حقنها يدويًا في الوكيل المختار.
5. **لا مفاتيح في المتصفح ولا في المستودع.** الجمع الحي يمر حصريًا عبر
   `/api/university/collect` على الخادم.

## 5. واجهات البرمجة `/api/university/*`

| المسار | الطريقة | الغرض |
| --- | --- | --- |
| `/api/university/status` | GET | `{configured, mode, model, runtimeRecords, store, version}` — فحص البوابة بلا استهلاك |
| `/api/university/archive` | GET | سجلات الأرشيف الحي فقط (البذور مضمّنة في الحزمة) |
| `/api/university/collect` | POST | `{departmentId, query?, collectorId?, language}` — جمع حي من الإنترنت عبر Gemini + بحث Google؛ الرد `pending-review` دائمًا؛ بلا مفتاح ⇒ `mode: 'seed'` |
| `/api/university/synthesize` | POST | `{departmentId, language}` — مذاكرة الخلية العصبية للقسم (دمج + ترقية إصدار) |
| `/api/university/organize` | POST | `{language}` — دورة «المُنظِّم» كاملة: أكواد + فحص استشهادات + كشف تكرار + تقرير |
| `/api/university/lab/teach` | POST | `{departmentId, targetId, language}` — حزمة تعليم وكيل من «المعمل» (حتمية، بلا رصيد) |

المتغيرات البيئية: `GEMINI_API_KEY` (أو `API_KEY`) للجمع الحي · `UNIVERSITY_MODEL`
(اختياري — الافتراضي سلسلة نماذج الوكلاء) · `UNIVERSITY_RATE_PER_MINUTE` (افتراضي 10) ·
`UNIVERSITY_ARCHIVE_PATH` (اختياري — افتراضي `.admin-data/university-archive.json`،
لا يُرفع إلى git ويُعاد إنشاؤه تلقائيًا عند أي استضافة بقرص كتابة) ·
`UNIVERSITY_STORE` (اختياري — `firestore` | `file` | `memory`، يجبر الواجهة الخلفية).

الأرشيف الحي (ما جمعه الروبوت فعليًا) يُحفظ على الخادم فقط — عبر واحدة من ثلاث
واجهات خلفية تُختار تلقائيًا عند أول استخدام (`storeBackend()`):

| الواجهة | متى تُختار | الدوام |
| --- | --- | --- |
| **Firestore** (`universityArchive`) | عند وجود بيانات اعتماد خدمة (`FIREBASE_SERVICE_ACCOUNT_JSON` أو الاسم المكافئ `FIREBASE_SERVICE_ACCOUNT` المستخدم في مشروع Vercel الحقيقي، أو `GOOGLE_APPLICATION_CREDENTIALS` يشير لملف JSON) | **دائم** — ينجو من إعادة النشر على Vercel |
| ملف JSON على القرص | لا توجد بيانات اعتماد Firestore + قرص قابل للكتابة | دائم ما دام القرص باقيًا (VPS/خادم Node) |
| الذاكرة | لا هذا ولا ذاك (serverless بلا اعتمادات، أو `/tmp` للقراءة فقط) | ينمحي مع العملية — ويرد `persisted: false` بصراحة |

**Firestore بصيغته الحالية مجاني تمامًا** ضمن طبقة Spark: ١ غيغابايت تخزين،
٥٠٬٠٠٠ قراءة/يوم، ٢٠٬٠٠٠ كتابة/يوم — والأرشيف الحي محدَّد بـ 500 سجل صغير كحد
أقصى، وعمليات الكتابة تحدث فقط عند تشغيل جامع/خلية/«المُنظِّم» يدويًا. التكلفة
المتوقعة: صفر. إن تجاوز التطبيق حدود الطبقة المجانية يتوقف Firestore عن التنفيذ
بدل أن يفوتر (على Spark)، وترد البوابة `persisted: false` بصراحة بدل ادعاء حفظ.

لتفعيل Firestore على Vercel (أو أي مضيف):

1. Firebase Console → المشروع `ai-studio-applet-webapp-18922` → ⚙️ Project settings
   → Service accounts → **Generate new private key** (ملف JSON — لا يُرفع إلى git أبدًا).
2. Vercel → Project → Settings → Environment Variables → أضف
   `FIREBASE_SERVICE_ACCOUNT_JSON` بقيمة محتوى ملف الـ JSON كاملًا في سطر واحد
   (Production + Preview). ملاحظة واقعية: مشروع Vercel الحقيقي يحمل بالفعل
   متغير `FIREBASE_SERVICE_ACCOUNT` (production فقط) — البوابة تقرأ كلا الاسمين،
   والـ JSON الملصوق بأسطر حقيقية داخل `private_key` يُصلَّح تلقائيًا قبل الفك.
3. (اختياري) `FIREBASE_FIRESTORE_DATABASE_ID` — الافتراضي قاعدة بيانات INSCO
   المسماة `ai-studio-inscointeractive-2ab74c2d-acdd-4fa3-a16b-53ea46221179` (نفس
   المستخدمة في `firebase-applet-config.json`)، و`FIREBASE_PROJECT_ID` إن اختلف المشروع.
4. أعد النشر — ستظهر `store: 'firestore'` في `/api/university/status` و«ARCHIVE →
   Firestore — دائم» في واجهة الجامعة.

**الأمان:** الكتابة تتم بصلاحية Admin SDK من الخادم فقط — لا تكتب من المتصفح أبدًا.
`firestore.rules` تبقى `default-deny` كما هي (لا يفتح بوابة جديدة، ولا تُضعف).
سجلات الأرشيف تُتحقق بنيويًا عند الكتابة والقراءة (كود، HTTPS، حالة، إصدار) ولا
يتجاوز حجم المجموعة 500 سجل (الأقدم يُزال بترتيب `updatedAt`). ملف الخدمة لا يُرتكب
في المستودعر أبدًا — متغيرات البيئة فقط.

النشر: نفس كود البوابة يعمل في ثلاثة مضيفات — `server.ts` (خادم Node للتطوير
والاستضافة بقرص)، و`api/university.ts` على Vercel (دالة serverless بحد 60 ثانية،
مُعاد توجيهها من `/api/university/:path*`)، ونفس الشيء تُديره أكاديمية إنسكو على
GitHub Pages عبر `VITE_AI_BASE_URL` أو العنوان المباشر للبوابة المستضافة. الدالة تحوي
CORS بنفس سياسة بوابة الذكاء الاصطناعي (أصول المشروع فقط: Pages وVercel ومعايناتها
ومضيفو التطوير المحليون؛ غير ذلك 403 في الـ preflight). الأرشيف المبدئي المُراجع
مضمّن في الحزمة ولا يحتاج قرصًا ولا مفتاحًا.

## 6. الواجهة (٦ أجنحة)

العمادة والمجلس (خريطة تنظيمية + خط التشغيل) · التخصصات الاثنا عشر (بطاقات السجلات
الموثقة مع مصادرها) · روبوتات الجمع (اختيار القسم والروبوت والتركيز + خط مراحل المهمة) ·
الخلايا العصبية (تشغيل المذاكرة وعرض تقرير الدمج) · الأرشيف العلمي (بحث وفلاتر وإحصاءات
حية + زر «شغّل روبوت التنظيم والهيكلة») · **المعمل** (توليد/نسخ/تنزيل حزمة تعليم الوكيل).

سجل عمليات حية (`details` أسفل الصفحة) يعرض كل قرار يتخذه العميد أو المًنظِّم أو الخلية.

## 7. الاختبارات

`npm run test:university` — 14 اختبارًا: سلامة الفهرس (12 تخصصًا · 24 جامعًا · 12 خلية)،
اكتمال الأرشيف المبدئي 100%، صمود «المُنظِّم» أمام سجلات بلا مصدر أو باستشهادات غير HTTPS،
دمج «الخلية» (إصدار + اتحاد مصادر + عودة للمراجعة)، حزم «المعمل»، وفحص ترميز العقود،
مع فحص تصيير عربي للواجهة. الاختبارات محروسة أيضًا ضمن `npm test` العام وفي
`portalIsolation`/`academyStations` (المحطة السابعة و`#university`).
