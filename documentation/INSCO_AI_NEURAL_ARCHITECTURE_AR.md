# الهيكل العصبي الموحد لـ INSCO AI

## الهدف

تحويل وكلاء INSCO من مسارات منفصلة إلى منظومة ذكاء واحدة متصلة بكل أجزاء المنصة، مع قدرة بحث واستجلاب معلومات من الإنترنت عند السماح بذلك، واستمرار الوظائف الأساسية محلياً عند غياب أي مزود خارجي.

هذا التصميم يرفع جودة النظام تدريجياً، لكنه لا يدّعي أن محركاً محلياً حتمياً يساوي نموذجاً لغوياً كبيراً أو أن إضافة واجهة وحدها تمنح وصولاً كاملاً للإنترنت.

## ما كشفته مراجعة الكود الحالية

- يوجد عقل محلي باسم `insco-local-1`، ويعتمد في جزء مهم منه على استرجاع نصوص مكتبة INSCO وبناء إجابات منظمة.
- البحث الحالي في `src/ai/search.ts` بحث معجمي BM25 وتوسيع مصطلحات ثنائي اللغة؛ ليس بحث embeddings دلالياً ولا زاحف إنترنت.
- الوكلاء الحاليون: Tutor وUser Copilot وSite Manager وCommunity Assist، ولكل منها مسارات في `server/ai/gateway.ts`.
- إعداد `AI_PROVIDER` يحدد المسار، والوضع الافتراضي الحالي `local`. يجب ألا نخلط بين هذا الوضع وبين `auto` قبل توحيد التنفيذ.
- عقد `src/ai/agentsContract.ts` يعرّف أوضاعاً متقدمة لوكيل ChatGPT مثل `web_search` و`deep_research` و`vision_ndt`، لكن وجود العقد لا يثبت وجود تنفيذ تشغيلي مكتمل لهذه القدرات. لم يظهر في مراجعة مسارات Gateway الحالية تنفيذ موصول ومكتمل لمسار البث الخاص بهذا الوكيل.
- لذلك المرحلة الأولى هي بناء طبقة أدوات وتوجيه موحدة، لا مجرد تغيير أسماء النماذج أو إضافة وصف تسويقي.

## الهيكل المستهدف

```text
واجهة INSCO الموحدة
        |
موجّه الطلبات + سياق الصفحة + صلاحيات المستخدم
        |
منسّق مركزي (Planner / Orchestrator)
        |
بوابة الأدوات والسياسات (Tool Gateway)
  |          |          |           |
بحث الويب   مكتبة INSCO  بيانات الموقع  أدوات NDT والمحاكاة
  |          |          |           |
مصادر موثقة / نتائج منظمة / نتائج تنفيذ فعلية
        |
طبقة المعرفة الموحدة (فهرس + روابط + صلاحيات + مصادر)
        |
مراجع الإجابة والتحقق والجودة
        |
المحادثة / تقرير / إجراء مقترح للمستخدم
```

### 1. المنسّق المركزي

- يصنّف الطلب: سؤال معرفي، بحث ويب، بحث معمق، تحليل ملف، حساب هندسي، إجراء داخل الموقع، أو مهمة مركبة.
- يضع خطة قصيرة ويختار الوكيل المتخصص والأدوات اللازمة.
- يمرر أقل قدر لازم من سياق الصفحة والبيانات.
- يجمع النتائج ويزيل التكرار ويتحقق من تعارض المصادر.
- لا ينفذ إجراءً مؤثراً (نشر، حذف، إرسال RFQ، تعديل بيانات) دون صلاحية واضحة وتأكيد المستخدم حيث يلزم.

### 2. الوكلاء المتخصصون

- **NDT Technical Agent:** RT وUT وPAUT وMT وPT وVT وPWHT، مع إلزامية ذكر الكود والإصدار ومعيار القبول والمصدر عند توافرها.
- **Research Agent:** بحث ويب، فتح صفحات عامة، استخراج نقاط مرتبطة بالسؤال، ومقارنة المصادر.
- **Academy Tutor:** ربط الشرح بالدروس والكتب والاختبارات والمحاكيات.
- **Community Agent:** فهم المنشورات والمناقشات وصياغتها وتلخيصها.
- **Site Operations Agent:** قراءة مؤشرات التشغيل وفق صلاحيات الإدارة، دون كشف بيانات إدارية لمستخدم عادي.
- **Document & Vision Agent:** استخراج النص والجداول وتحليل الصور والرسومات؛ تظل قدرات الرؤية المحلية معلّمة بوضوح إذا لم يتوفر نموذج محلي مناسب.
- **Engineering Tools Agent:** الحسابات والوحدات والمعادلات وأدوات NDT الحتمية القابلة للاختبار.

الوكلاء متخصصون لكنهم لا يملكون صلاحيات مستقلة؛ كل استدعاء يمر من بوابة الأدوات نفسها.

### 3. الوصول إلى الإنترنت

المطلوب هو وصول بحثي واسع ومنضبط، وليس اتصالاً عشوائياً مفتوحاً من كل وكيل:

1. واجهة موحدة مثل `searchWeb` و`openPublicPage` و`extractPage` و`compareSources`.
2. مزود البحث قابل للاستبدال، ويمكن إضافة أكثر من مزود لتقليل الاعتماد على خدمة واحدة.
3. لا تُفتح إلا روابط HTTP/HTTPS العامة؛ تُمنع عناوين الشبكات الداخلية وlocalhost وعناوين metadata الخاصة بالسحابة، مع إعادة فحص كل تحويل redirect لمنع SSRF.
4. حدود للوقت والحجم وعدد الصفحات والطلبات، وقائمة أنواع ملفات مسموح بها، وتنقية HTML قبل عرضه على النموذج.
5. محتوى صفحات الإنترنت بيانات غير موثوقة: لا ينفذ تعليمات الصفحة ولا يتيح لها تجاوز سياسة النظام أو استخراج الأسرار.
6. حفظ عنوان المصدر واسم الناشر وتاريخ النشر/الوصول ومقتطف الدليل، وإرفاق روابط المصادر بالإجابة.
7. عند تعذر الإنترنت، يواصل الوكيل باستخدام مكتبة INSCO ويصرح بوضوح أن البحث الحي لم يتم.

**مهم:** الوصول إلى كل معلومة منشورة حرفياً غير ممكن ضمانه؛ بعض المواقع محجوبة أو تتطلب حساباً أو اشتراكاً أو تمنع الفهرسة. لن نتجاوز تسجيل الدخول أو الحماية أو حقوق الوصول.

### 4. الذاكرة والمعرفة المشتركة

- ذاكرة محادثة قصيرة المدى منفصلة لكل جلسة ومستخدم.
- ذاكرة تفضيلات طويلة المدى بموافقة وسياسة احتفاظ واضحة.
- فهرس موحد لمحتوى الأكاديمية والمجتمع والوثائق المصرح بها وبيانات المنصة.
- بحث هجين: BM25 + embeddings عند توافر نموذج تضمين مناسب + إعادة ترتيب النتائج.
- كل وثيقة تحمل مصدرها ومالكها ومستوى سريتها وصلاحيات قراءتها وتاريخ تحديثها.
- لا تختلط ذاكرة المستخدم بذاكرة الشركة، ولا تنتقل الملفات الخاصة إلى مزود خارجي افتراضياً.

### 5. طبقة أدوات الموقع

بدلاً من أن يقرأ الوكيل قاعدة البيانات مباشرة، تُنشأ واجهات typed محددة مثل:
- `searchAcademy`
- `getCurrentPageContext`
- `searchCommunity`
- `getPublicCompanyInfo`
- `getAuthorizedClientDossier`
- `getAdminTelemetry`
- `runNdtCalculator`
- `runSimulation`

كل أداة تتحقق من هوية المستخدم وصلاحياته على الخادم، وتعيد أقل بيانات لازمة. لا تُقبل صلاحيات مرسلة من المتصفح كدليل موثوق.

### 6. التحقق من الجودة

- فصل الحقائق المسترجعة عن الاستنتاجات والاقتراحات.
- مراجع لكل ادعاء تقني حساس متى أمكن.
- مراجعة ثانية للإجابات عالية المخاطر: الكود، القبول/الرفض، السلامة، والنتائج الهندسية.
- إذا تعارضت المراجع أو لم تتوفر نسخة الكود المطلوبة، يوضح النظام ذلك ولا يخترع رقماً أو بنداً.
- تسجيل بيانات تشغيل غير حساسة: الأداة، زمن التنفيذ، حالة النجاح، نوع المصدر، ورمز الخطأ؛ دون تخزين أسرار أو نصوص خاصة بلا داعٍ.

## خطة التنفيذ المقترحة

### المرحلة A — توحيد العقل والتوجيه
- استخراج قرار اختيار المحرك وسياسة الخصوصية إلى وحدة مركزية.
- جعل `auto` ينفذ المحلي أولاً في الوكلاء الأربعة فعلياً.
- توحيد fallback عند غياب المفتاح والمهلة و429 و5xx وفشل المزود.
- إظهار المحرك الفعلي ومصدر الإجابة في metadata.

### المرحلة B — بوابة الإنترنت
- تعريف عقود أدوات البحث وفتح الصفحات.
- تنفيذ موفر بحث واحد أولاً، مع قابلية إضافة بديل.
- إضافة حماية SSRF وحدود الاستخدام وتنقية المحتوى.
- إضافة اختبارات المصادر والروابط والتحويلات والمهلات وانقطاع الإنترنت.

### المرحلة C — العقل العصبي المشترك
- منسّق مركزي وخطة أدوات قابلة للتتبع.
- تسجيل الوكلاء كمهارات مستقلة بعقود موحدة.
- ذاكرة جلسة وسياق صفحة موحدان مع احترام الصلاحيات.
- بث مراحل العمل والنتائج والمصادر إلى واجهة المحادثة.

### المرحلة D — ربط أقسام الموقع
- الأكاديمية والمكتبة والمحاكيات أولاً.
- المجتمع والملفات وطلبات العملاء ثانياً، وفق صلاحيات دقيقة.
- الإدارة ومؤشرات التشغيل أخيراً، وبوصول إداري فقط.
- إجراءات الموقع تبدأ بوضع القراءة والاقتراح، ثم تتطلب تأكيداً قبل الكتابة.

### المرحلة E — البحث الدلالي والملفات والرؤية
- embeddings وإعادة ترتيب النتائج وقياس الجودة على أسئلة INSCO.
- PDF والجداول والصور والرسومات مع حفظ مواضع المصادر.
- نموذج رؤية محلي فقط إذا كانت الجودة والموارد تسمحان؛ وإلا يكون المزود الخارجي اختيارياً وفق سياسة البيانات.

### المرحلة F — اختبارات وإطلاق تدريجي
- اختبارات لكل أداة ووكيل، واختبارات تكامل وصلاحيات وتسريب بيانات.
- اختبارات تشغيل محلي دون أي مفاتيح خارجية.
- اختبارات بحث ويب حي وفشل مزود البحث.
- اختبارات عربية وإنجليزية وSSE والأحمال.
- تشغيل تجريبي على فرع منفصل، ثم مراجعة PR، ثم دمج ونشر بعد نجاح التحقق.

## تعريف الإنجاز

لا نعتبر النظام مكتملاً لمجرد أن الوكلاء يستطيعون استدعاء نموذج خارجي. الإنجاز يعني أن الوكيل يختار الأداة الصحيحة، ويسترجع مصادر قابلة للتحقق، ويفهم سياق صفحة INSCO، ويحترم صلاحيات المستخدم، ويعود للمحلي عند تعطل الخارج، ويشرح حدود معرفته بدقة.

## الحالة

هذه وثيقة تصميم تنفيذية أضيفت إلى فرع التطوير. ليست ادعاءً بأن البحث المفتوح أو المنسق المركزي أو التكامل العصبي قد نُفذ بالفعل. الخطوة البرمجية التالية هي بناء عقود الأدوات وطبقة التوجيه المركزية واختبارها قبل توصيل جميع الوكلاء بها.
