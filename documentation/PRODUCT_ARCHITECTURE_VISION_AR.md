## 1. الرؤية

INSCO NDT EGY منظومة واحدة للتعليم والتدريب والمحاكاة والخدمات الهندسية والتواصل المهني، وليست مجموعة صفحات مستقلة. هدف تجربة المستخدم أن يعرف دائماً:
- أين هو الآن؟
- ما الخطوة المنطقية التالية؟
- كيف ينتقل بين التعلم والتطبيق والتقييم دون فقدان السياق؟
- أين يجد المساعدة أو الدعم؟

المبدأ الهندسي: الحفاظ على كل وظيفة وبياناتها الحالية، وإعادة تنظيم الروابط وتجربة الاستخدام حول رحلات واضحة، دون استبدال الأنظمة المستقرة أو تكرارها.

## 2. جرد الوظائف الموجودة في المستودع

هذا جرد للمناطق الواضحة في المصدر والتوثيق الحالي، وليس ادعاءً بأن كل تكامل خارجي مهيأ في بيئة الإنتاج:

| المنظومة | الموجود في المصدر | ملاحظات التكامل |
|---|---|---|
| بوابة الشركة | CompanyPortal، صفحات عائلات الخدمات، عروض فنية ومحاكيات توضيحية | المسار التجاري وخدمات NDT/PWHT |
| الأكاديمية | AcademyContent، المناهج، التخصصات، الكتب وEDB، الاختبارات والتقييم العملي | التحميل الكسول يفصل محتوى الأكاديمية عن صفحة الشركة |
| مسارات التعلم | أقسام choose / learn / practice / test / progress / mentor / university | تجميع التبويبات قائم في src/utils/portalRoutes.ts |
| المحاكيات | UT/PAUT وRT وPWHT وأدوات ومعامل أخرى | يلزم ربط كل درس بالمحاكي الصحيح مع الحفاظ على الروابط القديمة |
| المهندس الافتراضي | tutor، بحث محلي ومصادر، تدفق SSE وإيقاف الشرح | يجب أن يظل واعياً بالدرس الحالي؛ مزامنة التقدم عبر الأجهزة ليست مثبتة في المسودة #94 |
| الذكاء الاصطناعي | User Copilot، Site Manager، Community Assist، Tutor، ChatGPT streaming route | عقود وواجهات API موجودة؛ لا تساوي وحدها منصة وكلاء ذاتية طويلة التشغيل |
| المجتمع المهني | NetworkPortal ومكونات الملف الشخصي والتغذية والمجموعات والوظائف | يحتاج إلى اتساق الرحلة مع حساب المستخدم والأكاديمية |
| بوابة العملاء | ClientPortal وطلبات العملاء والشركات والملفات والحضور | لا تخلط بيانات العميل الخاصة مع المجتمع العام أو البحث العام |
| الإدارة | AdminPortal، دخول وكلمات مرور مرور/Passkeys، الطلبات والإعلانات ومصنع البرمجيات | يجب أن تكون مركز تحكم بصلاحيات واضحة لا نقطة تجاوز للأمان |
| اللغات والتنقل | portalRoutes وglobalLanguageSync وlanguages وtranslationStore | يجب الحفاظ على الروابط العميقة والروابط القديمة وRTL/LTR |
| النشر | GitHub Pages من main/docs وفق README | كل تعديل مصدر يتطلب بناء docs وفحص تطابقها |

### حقيقة مهمة عن الوكلاء

يوجد حالياً محرك محلي حتمي `src/ai/brain/` وعقود وواجهات لعدة مساعدين/وكلاء. المحرك المحلي يجيب من المعرفة والبيانات والقواعد، وهو قابل للاختبار دون شبكة. هذا لا يثبت وجود Orchestrator مستقل بجدولة مستمرة، أو طابور مهام دائم، أو ذاكرة مشتركة بين الوكلاء، أو تنفيذ تلقائي لكل أعمال الإدارة. هذه قدرات مستهدفة يجب تصميمها وإضافتها بعد جرد الموجود، لا افتراض أنها تعمل الآن.

## 4. خريطة التنقل المستهدفة

- الشركة: الرئيسية ← الخدمات ← تفاصيل الخدمة ← العرض الفني/طلب عرض السعر.
- الأكاديمية: اختيار التخصص والمسار ← التعلم ← التدريب العملي ← الاختبار ← متابعة التقدم ← طلب المساعدة.
- المجتمع: التغذية ← المناقشات والمجموعات ← الملف المهني ← الفرص.
- العميل: التسجيل والتحقق ← الطلبات ← ملفات الشركة والتقارير ← متابعة الحالة.
- الإدارة: لوحة القيادة ← الوحدة الإدارية ← سجل النشاط والموافقات.

تظل المسارات الحالية في `src/utils/portalRoutes.ts` هي المرجع؛ أي إعادة تنظيم يجب أن تحافظ على legacy hashes والروابط العميقة القابلة للمشاركة.

## 5. رحلة الطالب المرجعية

1. يفتح الأكاديمية ويختار تخصصاً ومستوى.
2. يحصل على مسار واضح ومتطلبات سابقة وخطوة تالية.
3. يدرس درساً موثقاً بأهداف ومصادر.
4. يسأل المهندس الافتراضي مع الاحتفاظ بسياق الدرس.
5. ينتقل إلى المحاكي المرتبط بالدرس عند توفره.
6. ينفذ تمريناً أو تقييماً عملياً.
7. يرى نتيجة مفهومة وما يحتاج إلى مراجعته.
8. يُحفظ تقدمه ويعود إلى نفس النقطة لاحقاً.
9. يشارك في المجتمع دون كشف بيانات العميل أو بيانات خاصة.

## 7. متطلبات منظومة الوكلاء المستهدفة

قبل إضافة أي وكيل جديد، يجب حصر الوظائف الحالية وإعادة استخدام الموجود. الطبقات المقترحة:
1. Orchestrator يوزع المهام على أدوات/وكلاء متخصصين.
2. Task Queue بمهام ذات حالة ومحاولات ومهل زمنية.
3. Memory scoped حسب المستخدم والجلسة والوظيفة، مع سياسات احتفاظ.
4. Tool permissions: قراءة، اقتراح، كتابة محدودة، وإجراءات تتطلب موافقة.
5. Audit log لكل طلب ومدخلات مسموح بها ومخرجات ونتيجة.
6. Admin control لإيقاف وكيل أو مهمة ومراجعة التكلفة والأخطاء.

لا حذف، ولا نشر، ولا دمج، ولا تعديل صلاحيات أو أسرار، ولا إرسال رسائل أو نشر محتوى نيابة عن المستخدم دون موافقة صريحة مناسبة. لا ترسل بيانات العميل أو بيانات الإدارة إلى مزود خارجي إلا وفق إعداد واضح وموافقة وسياسة خصوصية.

## 8. أولويات التنفيذ

### P0 — تثبيت خط الأساس
- حصر الفروع وطلبات الدمج المفتوحة وتعارضاتها.
- تشغيل بوابة التحقق على آخر main.
- فصل أخطاء كل فرع عن أخطاء main.
- تحديد الفرع المرجعي وعدم نسخ ملفات docs المبنية من فرع آخر.

### P1 — وضوح تجربة المستخدم
- تدقيق جميع الشاشات الأساسية على الهاتف والكمبيوتر.
- تبسيط الصفحة الرئيسية واختيار البوابة.
- توحيد أسماء الأقسام والرموز وأزرار الإجراء.
- جعل كل صفحة تعرض: المكان الحالي، الهدف، والخطوة التالية.
- الحفاظ على الروابط القديمة والتنقل بلوحة المفاتيح.

### P2 — إكمال رحلة التعلم
- توصيل معرف الدرس بالمهندس الافتراضي والمحاكي والاختبار.
- حفظ checkpoints بطريقة واضحة، مع بيان حدود التخزين المحلي.
- توحيد تقدم الطالب دون دمج مصادر تقدم مختلفة بلا عقد واضح.

### P3 — الإدارة والوكلاء
- جرد endpoints والوكلاء والأدوات الموجودة.
- تصميم orchestration وqueue وmemory وpermissions وaudit.
- إطلاق read-only monitoring أولاً، ثم إجراءات محدودة بموافقة.

### P4 — المجتمع والخدمات
- ربط الهوية والملف المهني مع ضوابط الخصوصية.
- إتاحة مشاركة نتائج تعليمية اختيارية بعد مراجعة المستخدم.
- ربط طلبات الخدمات بحسابات العملاء والإدارة.

### P5 — ضمان الجودة والإصدار
- Type-check، الاختبارات، EDB، بناء الإنتاج، تطابق docs.
- اختبارات مسارات المستخدم واللغتين وإمكانية الوصول.
- مراجعة أمنية لعزل الحسابات والبوابات.
- موافقة المالك قبل الدمج والنشر.

- بقيت الوظائف والبيانات الحالية سليمة.
